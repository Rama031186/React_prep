SECTION 01

The Mental Model

React's core idea: a component is a function that takes props and state and returns a description of UI. When state changes, React re-runs that function, compares the new description to the old one (reconciliation), and updates only what changed in the real DOM.

Modern React changes how much performance work you manage by hand. The React Compiler can automatically memoize components and values, reducing the need to routinely sprinkle memo, useMemo, and useCallback through new code.

The three triggers for a re-render

  • Own state changed. A state setter was called with a new value.
  • A parent re-rendered. The child is rendered again as part of its parent's render.
  • A subscribed context changed. A Context value read by this component was updated.
QUICK DECISION RULE · WHICH TRIGGER IS IT?
  1. Did a state setter run with a new value? That's the trigger.
  2. No state change, but a parent rendered? Trace upward to the component that did.
  3. Neither, but the component reads Context? Check the provider value.
  4. Still unclear? Log during render and reproduce the interaction.
Interview tip. “A component re-renders when its own state changes, its parent re-renders, or a context it subscribes to changes. React then reconciles the returned tree against the previous one and patches the DOM nodes that differ.”

What interviewers usually want to hear

  • You can state the three triggers without hesitation.
  • You understand reconciliation compares tree descriptions; React does not simply redraw the whole page.
  • You know what the Compiler handles automatically versus what remains manual.

Good default: components are functions of state; re-renders come from state, parent, or context changes; reconciliation patches what changed.

SECTION 02

State & Re-renders

State updates are batched. Reading state immediately after setting it still gives you the value from the current render because the next render has not happened yet.

STALE CLOSURE VS FUNCTIONAL UPDATER
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    console.log(count); // old value from this render

    // Each updater receives the latest queued value
    setCount(c => c + 1);
    setCount(c => c + 1);
  }
}

Calling setCount(count + 1) twice closes over the same count, so the updates do not stack as two increments. The functional updater form receives the latest queued value each time.

WHEN TO USE THE FUNCTIONAL UPDATER
  1. New state depends on previous state? Use setX(x => ...).
  2. New state is independent? A plain setter is fine.
  3. Need the new value immediately? Compute it yourself or read it on the next render; don't expect the setter to mutate the current closure.
Interview tip. Use the functional updater whenever the next value depends on the previous one. It stays correct when several updates are queued in one event handler.

What interviewers usually want to hear

  • State reads after a setter still reflect the current render's closure.
  • You use functional updates when state depends on its previous value.
  • You understand automatic batching in modern React.

Good default: use functional updates for dependent state changes, and don't read a setter's result from the same render.

SECTION 03

useEffect: Deps, Cleanup, When Not To

useEffect synchronizes a component with something outside React: a subscription, timer, browser API, or imperative DOM integration. It is not a general-purpose “run this when something changes” mechanism.

The dependency array

DEPENDENCY ARRAYWHEN IT RUNS
OmittedAfter every render.
[]After the initial mount (with development Strict Mode considerations).
[a, b]After mount and when a dependency changes.
DERIVED STATE VIA EFFECT · ANTI-PATTERN
// Avoid: extra render and briefly stale UI
const [fullName, setFullName] = useState('');
useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);

// Prefer: derive during render
const fullName = `${firstName} ${lastName}`;

If a value can be calculated from props or state during render, it usually does not belong in an effect. Effects are for synchronization with external systems.

COULD THIS JUST BE COMPUTED DURING RENDER?
  1. Derived from props or state? Calculate it during render.
  2. Subscription, timer, external fetch lifecycle, or DOM integration? An effect may be appropriate.
  3. Event-handling logic such as a button click or form submit? Put it in the event handler or an Action.
  4. When an effect sets up something, return cleanup to undo it.
Interview tip. Before reaching for useEffect, ask whether the value can be computed during render. If it can, an effect adds unnecessary complexity and an extra render.

Good default: use effects to synchronize with external systems; compute derived values during render; keep user-event logic in event handlers or Actions.

SECTION 04

The Compiler Era, Do You Still Need memo?

The React Compiler automates many memoization optimizations for components and values when it can safely analyze your code. That changes manual memoization from a routine default to a deliberate tool.

TOOLWHAT IT DOES / MODERN GUIDANCE
React.memoHistorically skips renders when props are shallow-equal. Compiler can often apply equivalent optimization automatically.
useMemoCaches a calculation. Manual use is useful when the Compiler cannot safely optimize or in non-compiled code.
useCallbackStabilizes a function reference. Compiler can handle many common cases.

The Compiler does not remove the need to understand memoization. Pure render functions and the Rules of React remain essential. Existing codebases may not have the Compiler enabled.

MANUAL MEMOIZATION DECISION
  1. Compiler enabled and code follows the Rules of React? Usually let it optimize.
  2. Legacy or non-compiled code? Memoize when a measured cost justifies it.
  3. Compiler cannot analyze a value safely? Manual memoization may still help.
  4. Always keep render functions pure and avoid mutating props or state.
Interview tip. “I lean on the Compiler for routine memoization in new code, but I still understand memo, useMemo, and useCallback for existing projects and cases the Compiler cannot optimize.”

Good default: don't sprinkle memoization everywhere; understand the cost, the Compiler, and the codebase you are working in.

SECTION 05

Actions, useActionState & useOptimistic

React Actions provide a model for async mutations such as form submissions. They integrate pending state, results, and optimistic UI rather than requiring every form to hand-wire several pieces of state.

APIWHAT IT GIVES YOU
ActionsAsync functions used with forms or transitions; React can track pending work.
useActionStateConnects an Action to its returned state and pending status.
useFormStatusLets a child read the pending status of its nearest parent form.
useOptimisticShows an optimistic value while an Action is in progress; the UI can revert if it fails.
useActionState PATTERN
function AddComment({ addCommentAction }) {
  const [state, formAction, isPending] = useActionState(
    addCommentAction,
    { error: null }
  );

  return (
    <form action={formAction}>
      <input name="comment" />
      <button disabled={isPending}>
        {isPending ? 'Posting…' : 'Post'}
      </button>
      {state.error && <p>{state.error}</p>}
    </form>
  );
}
WHICH ACTION API?
  1. Form submission with pending and result/error state? useActionState.
  2. Child needs the nearest form's pending state? useFormStatus.
  3. Instant feedback that may need rollback? useOptimistic.
  4. Background async work without form state? A normal async function or transition may be enough.

Good default: Actions for mutations, useActionState for result and pending state, and useOptimistic for immediate feedback.

SECTION 06

The use() Hook & Suspense

use() can read the value of a Promise or Context during render. Unlike ordinary hooks, it can be called conditionally and inside loops. When a Promise is pending, the component suspends and the nearest Suspense boundary can show its fallback.

use() WITH A PROMISE
function Comments({ commentsPromise }) {
  // Promise should be stable and created outside this render
  const comments = use(commentsPromise);
  return comments.map(comment => (
    <Comment key={comment.id} {...comment} />
  ));
}

<Suspense fallback={<Spinner />}>
  <Comments commentsPromise={cachedCommentsPromise} />
</Suspense>

Do not create a fresh Promise inline on every render. Keep it stable in a parent, cache, or data-fetching layer and pass it into the component.

PROMISE STABILITY
  1. Promise created outside the component and passed in? Stable; suitable for use().
  2. Promise created fresh in the component body? Avoid; it can repeatedly suspend.
  3. Need parameterized fetching? Cache promises by the relevant parameter.
Interview tip. “use() reads a Promise or Context during render. For Promise reads, I pass a stable Promise and wrap the suspending component in Suspense.”

Good default: use a stable Promise with a Suspense boundary; don't create a new Promise on every render.

SECTION 07

Server vs Client Components

Server Components run on the server and are the default in frameworks that support React Server Components. Client Components are used where interactivity, state, effects, event handlers, or browser APIs are required.

TYPECAN / CANNOT
Server ComponentCan access server-side resources and render on the server. Cannot use client hooks such as useState or browser event handlers.
Client ComponentCan use state, effects, event handlers, and browser APIs. Cannot directly access server-only resources or secrets.

Server Components can render Client Components. A Client Component should not import a Server Component directly; instead, server-rendered content can be passed through props or children.

SERVER OR CLIENT?
  1. Default to Server Components when the framework supports them.
  2. Need state, effects, browser APIs, or event handlers? Use a Client Component.
  3. Need a database or secret? Keep that work server-side.
  4. Push the client boundary as low in the component tree as practical.
Interview tip. “I'd default to Server Components and add a small Client Component boundary only around the interactive parts. That avoids shipping unnecessary JavaScript to the browser.”

Good default: server by default; client only where interactivity is needed; keep server-only resources out of client bundles.

SECTION 08

Context vs External State Libraries

Context solves prop drilling; it is not automatically a high-performance state-management solution. Consumers re-render when the Context value they read changes.

TOOLBEST FOR / WATCH OUT FOR
useState / useReducerLocal component state. Lift only as far as sharing requires.
ContextLow-frequency shared values such as theme, locale, or auth. Broad updates can re-render consumers.
Zustand / Redux / JotaiComplex or frequently updated cross-cutting state. Adds concepts and dependencies.
Server-state toolsFetched data with caching, revalidation, and staleness; treat it differently from local UI state.
WHICH STATE TOOL?
  1. Only one component needs it? useState or useReducer.
  2. A few distant components need a rarely changing value? Context.
  3. Many components need frequent updates with performance requirements? Consider an external store.
  4. Data belongs to a server? Use a server-state or framework data-fetching approach.

Good default: local state first, Context for infrequent shared values, external stores when complexity or update frequency justifies them, and dedicated handling for server state.

SECTION 09

Custom Hooks & Composition Patterns

A custom Hook is a function that calls other Hooks. Its value is extracting reusable stateful logic so components can focus on rendering.

A REAL CUSTOM HOOK · useDebouncedValue
function useDebouncedValue(value, delay) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer);
  }, [value, delay]);

  return debounced;
}

// Usage
const debouncedQuery = useDebouncedValue(query, 300);
WHEN TO EXTRACT A CUSTOM HOOK
  1. The same stateful logic is duplicated across components? Extract it.
  2. Only one component uses it once? Keep it inline until reuse appears.
  3. Does the function call no Hooks? It may simply be a regular helper function.

Prefer composition over configuration for flexible component APIs. Passing children or slots often scales better than adding many boolean props to one component.

Interview tip. Extract a custom Hook when stateful logic is genuinely reused, and prefer composition via children or slots over a component with an ever-growing list of configuration flags.

Good default: extract duplicated stateful logic, follow the Rules of Hooks, and compose components with children or slots.

SECTION 10

Common Mistakes & Pitfalls

The gap between “I know React” and “I interview well in React” is often in the details below.

MISTAKEWHY IT HURTSFIX
Mutating state directlyBreaks reference-based change detection and can create confusing UI.Create new arrays and objects with spread, map, or filter.
Missing or unstable list keysReact can associate component state with the wrong item after reorder.Use a stable unique ID, not an array index for reorderable lists.
Effect for derived valuesUnnecessary render and stale UI window.Compute derived values during render.
Fresh Promise inline for use()Suspense may never settle as expected.Cache the Promise and pass a stable reference.
Ignoring loading, error, or empty statesFeature feels incomplete and edge cases break.Design loading, error, empty, and success states explicitly.
Repeating outdated memoization adviceSignals that you have not followed modern React tooling.Know what the Compiler automates and when manual memoization remains useful.
ARE YOU SURE THAT FEATURE IS STABLE?
  1. Know the status of React APIs in the version and framework you use.
  2. Check official release notes before relying on newly introduced or Canary features.
  3. If unsure in an interview, state the uncertainty and explain how you would verify it.

Good default: avoid mutation, use stable keys, keep effects focused, model async UI states, and verify feature stability instead of guessing.

SECTION 11

Interview Quick Reference

Signal words and your response

IF THE QUESTION SAYSYOUR RESPONSE
“Why did this re-render?”Own state changed, parent rendered, or subscribed Context changed. Trace which one.
“How would you handle this form?”An Action with useActionState for pending and result state.
“Do you still need useMemo?”Compiler handles many cases; manual memoization remains for justified exceptions and non-compiled code.
“Server or Client Component?”Server by default; client boundary around the interactive leaf.
“How would you share state?”Escalate from local state to Context to an external store based on update frequency and complexity.
“Explain use().”Reads Promise or Context; Promise should be stable and used with Suspense.
WHAT WOULD YOU REACH FOR?
  1. Form mutation with pending and error state? Actions + useActionState.
  2. Instant feedback that may roll back? useOptimistic.
  3. Data that suspends while loading? use() + Suspense + stable Promise.
  4. Shared, rarely changing global value? Context.
  5. Shared, frequently changing state at scale? External store.

What interviewers usually want to hear

  • Fluent fundamentals: re-render triggers, keys, effect dependencies.
  • Current knowledge of the Compiler, Actions, use(), and Server Components.
  • A deliberate state-management escalation path.
  • Honesty about what is stable versus experimental.

Good default: fundamentals by reflex, modern React APIs understood conceptually, Server Components by default where supported, and no confident guessing about experimental features.
